# Kafka-to-Flink Link Simulation Pipeline

## Project Overview

This is a **SimPy → Kafka → Flink → Kafka** link simulation and processing pipeline used to generate distributed service call logs, and to perform parent-child link matching and aggregation by IP in Flink. The specific project requirements come from @requirements-v2.md.

- SimPy generates service call chains and sends them to Kafka
- Flink partitions by matching IP and links parent-child relationships
- Event-time Watermark + idle flush control output and state cleanup

## Architecture and Data Flow

1. `simpy_message_generator.py` generates call logs and writes them to Kafka (default topic: `test-topic`)
2. `flink-jobs/simpy_kafka_reader.py` reads from Kafka, performs parent/child matching by IP, and aggregates the output
3. The output is written back to the Kafka result topic (`KAFKA_OUTPUT_TOPIC`) and is also printed to the Flink log (stdout)

## Complexity and Performance

### Current Complexity (by IP key)

- `IpLinkingProcess`: Let `N` be the number of active messages (parent + child) under a given IP. Each new message scans all messages of the opposite role under that IP, so the worst case for a single event is `O(N)`; the overall worst case within one window is `O(N^2)` (more precisely `O(P*C)`). State memory is `O(N)` per IP until cleaned by the `end_at_ms` timer or idle flush.
- `MessageAggregationProcess`: Each message id maintains the base message plus parent/child lists. Each update rewrites the JSON list, so the cost of a single update is proportional to the list size; the total work per message is linearly related to the number of links. Memory grows with the number of associated parents/children until cleaned by `end_at_ms` or idle flush.
- `linking_utils.WatermarkMatcher` (testing/helper): Each message is compared against all buffered messages, and emitting also requires traversing the buffer; single-message cost is `O(N)`, overall worst case is `O(N^2)`, and memory is `O(N)`.

### Existing Performance Optimizations

- Partitioning by matching IP: limits chaining to a single key scope and improves parallelism.
- Event-time Watermark (`SIMPY_MAX_OUT_OF_ORDER_MS`) + `end_at_ms` timer: automatically cleans expired state to avoid unbounded retention.
- Idle flush (`SIMPY_IDLE_FLUSH_MS`): proactively cleans idle keys to reduce sparse-stream memory usage.
- Two-stage processing (linking → updates → aggregation): reduces repeated rewrites of full messages.

## Message Format

The format of a single message generated by SimPy is as follows (JSON):

```json
{
  "id": "msg_1",
  "src_ip": "10.0.0.1",
  "dst_ip": "10.1.0.2",
  "start_at_ms": 1700000000000,
  "latency_msec": 40.0,
  "end_at_ms": 1700000000040
}
```

The output aggregated by Flink appends `parents` / `children`:

```json
{
  "id": "msg_1",
  "src_ip": "10.0.0.1",
  "dst_ip": "10.1.0.2",
  "start_at_ms": 1700000000000,
  "latency_msec": 40.0,
  "end_at_ms": 1700000000040,
  "parents": [],
  "children": ["msg_2"]
}
```

## Link Matching Rules

The matching conditions for parent-child relationships are as follows (see `flink-jobs/linking_utils.py`):

- `parent.dst_ip == child.src_ip`
- `parent.start_at_ms <= child.start_at_ms`
- `parent.end_at_ms >= child.end_at_ms`

## Directory Structure

- `docker-compose.yml`: starts Zookeeper / Kafka / Flink
- `Dockerfile.flink`: Flink + Python runtime environment
- `simpy_message_generator.py`: SimPy call chain simulator
- `flink-jobs/simpy_kafka_reader.py`: main Flink job (link matching + aggregation)
- `flink-jobs/kafka_reader.py`: simple Kafka read example
- `flink-jobs/linking_utils.py`: matching rules and watermark utilities
- `produce_test_messages.py`: simple test message producer
- `test_chain_linking.py`: pure Python matching rule tests

## Quick Start

### 1) Start services

```bash
docker compose up -d
```

### 2) Submit the Flink job (link matching)

```bash
docker exec jobmanager ./bin/flink run -py /opt/flink/usrlib/simpy_kafka_reader.py
```

### 3) Generate simulated messages

```bash
# Continuous streaming generation
python simpy_message_generator.py --stream --interval 500 --realtime --ip-pool-size 6

# Fixed count
python simpy_message_generator.py --count 5 --interval 50 --realtime --ip-pool-size 3

# With jitter
python simpy_message_generator.py --count 5 --interval 100 --std-dev 200 --realtime --ip-pool-size 3

# Print message details
python simpy_message_generator.py --count 5 --interval 50 --realtime --print-msg --ip-pool-size 3
```

### 4) Watch the output

```bash
# Recent logs
docker logs taskmanager --since 1m 2>&1 | grep -E "^\\+I\\["

# Continuous follow
docker logs -f taskmanager 2>&1 | rg "\\+I\\[|linked_message"
```

```bash
# Read the results written back to Kafka
docker exec kafka kafka-console-consumer \
  --bootstrap-server kafka:29092 \
  --topic linked-topic \
  --from-beginning \
  --max-messages 5
```

## SimPy Generator Notes

### Call Chain Structure

The current simulated link structure is roughly:

- Client → Main
- Main calls SubService1 + SubService2 in parallel
- SubService2 then calls SubService3
- Main may call SubService2 a second time (about 40% probability)

### Command-Line Arguments

- `--realtime`: use a real-time clock (1 unit = 1 ms)
- `--count N`: generate N traces
- `--stream`: generate continuously (overrides `--count`)
- `--interval MS`: average interval (milliseconds)
- `--std-dev MS`: standard deviation of interval jitter
- `--print-msg`: print each message
- `--debug`: do not write to Kafka, local simulation only
- `--topic NAME`: Kafka topic (default `test-topic`)
- `--bootstrap HOSTS`: Kafka bootstrap (default `localhost:9092`)
- `--ip-pool-size N`: IP pool size for each service

### Delay and Out-of-Order Simulation (Environment Variables)

Messages are assigned random delay based on a chi-square distribution to create out-of-order behavior:

- `SIMPY_DELAY_CHISQ_DF` (default 2.0)
- `SIMPY_DELAY_SCALE_MS` (default 1000)
- `SIMPY_MAX_DELAY_MS` (default 30000)

## Flink Job Notes

### Watermark and State Cleanup

- Watermark is based on `start_at_ms`
- `SIMPY_MAX_OUT_OF_ORDER_MS`: maximum tolerated out-of-order time
- `SIMPY_IDLE_FLUSH_MS`: cleanup time for idle keys

### Kafka Configuration (Environment Variables)

- `KAFKA_TOPIC`: consumed topic
- `KAFKA_OUTPUT_TOPIC`: topic for writing back results
- `KAFKA_BOOTSTRAP`: Kafka broker
- `KAFKA_AUTO_OFFSET_RESET`: offset policy
- `SIMPY_PARALLELISM` / `KAFKA_PARTITIONS` / `KAFKA_NUM_PARTITIONS`: parallelism
